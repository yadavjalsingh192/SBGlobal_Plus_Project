# SBGlobal Plus Enterprise SaaS Core Transformation Recommendation

## Purpose

This document is the single source of truth for transforming the SBGlobal Plus Knowledge Base into the standard of a World-Class Enterprise Multi-Tenant SaaS Platform. It unifies the platform's core architecture with its public digital presence — corporate website, landing pages, and brand experience — under one conflict-free reference, ready to guide a fresh rewrite of the Knowledge Base's Markdown files (Section 13).

The reference project this Knowledge Base currently describes is a single-domain (LIS/Pathology) system. Transforming it does not require rebuilding that project from the ground up. It requires transforming its terminology, architecture documentation, and knowledge base so that they represent the SBGlobal Plus standard: healthcare-specific naming is removed from the core platform and replaced with enterprise-generic terminology, while healthcare itself remains fully supported as one of the platform's industry verticals (Section 5).

## 2. Strategic Goal

The core system is built to evolve continuously for the next 20–25 years — through Configuration, Metadata, Rules, Policies, Plugins, and AI — without dependency on developers for day-to-day business change.

The platform provides a seamless experience across Web, Mobile, and Windows Desktop. Users continue working even without internet connectivity; whenever connectivity is restored, the platform automatically and securely synchronizes data in the background without interrupting the user's workflow.

## 4. Platform Provisioning Model

One Enterprise Core serves every tenant. This section defines how a tenant is provisioned, what it receives, and how every login — regardless of client — is authenticated.

### 4.1 Tenant Onboarding Flow

1. **Single Enterprise Core** — one shared platform core powers every tenant.
2. **Tenant chooses a subscription plan** (Free, Starter, Premium, or Enterprise — see Section 12.3).
3. **Tenant receives:**
   - Tenant Application Website — a staff- and end-user-facing web portal for that tenant (distinct from the SBGlobal Plus corporate marketing website described in Section 12)
   - CMS
   - ERP Dashboard
   - Mobile Application (Android & iOS)
   - Windows Desktop Application (.exe)
   - Windows Installer Package (.msi)
   - REST API, Webhooks, and API Documentation
4. **Tenant configures** branding, themes, modules, workflows, notifications, and integrations — without modifying source code.
5. **Ready to Live.**

### 4.2 Access & Authentication Flow

Every login, on every client, follows the same server-authoritative sequence:

**Web / Mobile / Windows Desktop → Secure Login → HTTPS / REST API → Authentication Service → Tenant Validation → Subscription Validation → License Validation → Device Registration Validation → RBAC Permission Validation → JWT Access Token → Refresh Token → Platform Access Granted**

Without successful authentication, authorization, tenant validation, license validation, and server verification, no client application may access protected resources.

### 4.3 Identity & Authentication Framework

The platform supports a pluggable Identity and Authentication Framework. Authentication methods are configurable per Tenant, Role, Device, Platform, and Subscription Plan. Authentication providers are enabled or disabled through configuration and policy management — never through source code modification.

## 6. Security & Identity Architecture

Security is enforced end-to-end — at the network edge, in the authentication flow, in how tenant data is isolated, and in how the platform responds when something goes wrong.

### 6.1 Supported Authentication Methods

| Category | Methods |
|---|---|
| Credential-Based | Username & Password · Email & Password · Mobile Number & Password · Mobile OTP · Email OTP |
| Federated & Enterprise SSO | Google Sign-In · Microsoft Entra ID (Azure AD) · Apple Sign-In · Single Sign-On (SSO) · LDAP / Active Directory · OAuth 2.0 · OpenID Connect (OIDC) · SAML 2.0 |
| Passwordless & Biometric | Passkeys (FIDO2/WebAuthn) · Authenticator Apps (TOTP) · Hardware Security Keys · Face Authentication · Fingerprint Authentication · Iris Authentication · Biometric Authentication · Magic Link Authentication · QR Code Login · Passwordless Authentication |
| Machine & API Identity | API Token Authentication · Service Account Authentication |

All methods above are enabled, disabled, or combined per Tenant, Role, Device, Platform, or Subscription Plan through configuration — never through code changes (Section 4.3).

### 6.2 Digital Identity & Digital Signature Providers

The platform supports configurable Digital Identity and Digital Signature providers, including:

- Aadhaar eSign
- DigiLocker
- USB eToken
- Digital Signature Certificates (DSC)
- PKI Certificates
- Government Identity Providers
- Enterprise PKI
- Organization Certificates

### 6.3 Adaptive Authentication & Policy Configurability

The platform supports risk-based adaptive authentication, including:

- Trusted Devices
- Unknown Device Detection
- Impossible Travel Detection
- Geo-Fencing
- Geo-Restriction
- Login Time Restrictions
- Concurrent Session Control
- Multi-Factor Authentication (MFA)
- Step-Up Authentication

Authentication policies are configurable at the level of Tenant, User, User Group, Department, Organization, Device, Platform, Module, Location, and Subscription Plan.

### 6.4 Location, Device & Session Security Attributes

The platform supports configurable Location, Device, and Session Security attributes:

| Category | Attributes |
|---|---|
| Location | GPS Location · Latitude · Longitude · Address · Time Zone |
| Device | Device ID · Device Fingerprint · Operating System · Browser Information · Application Version |
| Network & Session | Public IP · Private IP · Network Type · Login Timestamp |

### 6.5 Multi-Tenant Data Isolation Model

Multi-tenancy is enforced at the data layer, not only at the application layer. The platform supports the following tenant isolation models, selectable per tenant tier:

| Model | Description | Typical Use |
|---|---|---|
| Silo (Dedicated) | Dedicated database (or dedicated schema) per tenant | Enterprise / regulated tenants requiring strict data residency |
| Bridge (Schema-Isolated) | Shared database, dedicated schema per tenant | Mid-size tenants balancing cost and isolation |
| Pool (Row-Level Isolation) | Shared database and schema, tenant-scoped row-level security enforced at the query layer | Starter / high-volume, low-customization tenants |

Regardless of model, every data access path is scoped to a validated tenant context established during authentication (Section 4.2); no query, cache key, background job, or exported report may cross tenant boundaries. Tenant-to-tenant data leakage is treated as a Critical-severity incident (Section 6.9).

### 6.6 Secrets & Cryptographic Key Management

"Everything Encrypted" (Section 3) is implemented through a centralized Key Management Service (KMS) / Hardware Security Module (HSM):

- Encryption at rest for all tenant data and backups; encryption in transit (TLS 1.2+) for all client-server and service-to-service traffic.
- Per-tenant data encryption keys, so a compromised key cannot expose data belonging to another tenant.
- Field-level encryption for sensitive personal data (health records, government identity numbers, payment details, biometric templates).
- Scheduled and on-demand key rotation, with retired keys kept only long enough to re-encrypt existing data.
- Application secrets, API credentials, and third-party integration keys held in a secrets vault — never in source code, configuration files, or client applications.

### 6.7 API Governance & Abuse Prevention

Because the platform is API First (Section 1), the API surface itself is a protected asset:

- Rate limiting and throttling, configurable per Tenant, Subscription Plan, and API Key, so one tenant cannot degrade service for others.
- Web Application Firewall (WAF) and DDoS protection in front of all public API and website endpoints.
- API versioning and a published deprecation policy, so tenant integrations are never broken without notice.
- Request signing and payload validation for webhooks, with automatic retry and dead-letter handling for failed deliveries.

### 6.8 Server-Authoritative Architecture & Trust Services

The platform follows a Server-Authoritative Architecture. Clients (Web, Mobile, and Windows Desktop) never directly access protected business resources without successful server authentication and authorization.

All business operations require:

- User Authentication
- Tenant Validation
- Subscription Validation
- License Validation
- Device Registration Validation
- Role & Permission Validation
- JWT Access Token Validation
- API Authorization

The platform supports configurable trust services, including:

- Digital Identity
- Digital Signature
- Digital Certificate Validation
- Timestamp Validation
- Certificate Revocation Checking
- Audit Evidence
- Non-Repudiation
- Certificate Transparency Validation
- OCSP / CRL Validation

Offline mode (Section 2) is available only to previously authenticated, authorized users, governed by the same configurable synchronization and security policies as online access.

### 6.9 Vulnerability Disclosure & Incident Response

- A published responsible-disclosure channel (e.g., security@sbglobalplus.com) through which researchers and customers can report vulnerabilities.
- A defined severity classification (Critical / High / Medium / Low) with target triage and remediation timelines for each.
- Scheduled third-party penetration testing and continuous automated vulnerability scanning of the platform and its dependencies.
- A documented incident response and breach notification process, including tenant and regulatory notification timelines consistent with applicable law (Section 7).

## 7. Compliance & Regulatory Framework

Enterprise buyers evaluate trust before they evaluate features. The platform maintains — and the public website (Section 12) visibly communicates — the following compliance posture:

- **SOC 2 Type II** attestation for security, availability, and confidentiality.
- **ISO/IEC 27001** certified information security management.
- **GDPR** readiness for tenants and end users in the European Union.
- **India's Digital Personal Data Protection (DPDP) Act, 2023** readiness, consistent with the platform's use of India-specific identity providers (Aadhaar eSign, DigiLocker — Section 6.2).
- **HIPAA readiness** for the Healthcare vertical (Section 5), including Business Associate Agreement (BAA) support where applicable.
- **PCI-DSS** alignment wherever payment data is processed (subscriptions, marketplace, affiliate payouts).

Tenants and their end users retain the right to:

- **Export** their full tenant data set on demand, in a portable format.
- **Request deletion** ("right to erasure") of their data, subject to legal and contractual retention requirements.
- Receive a **Data Processing Agreement (DPA)** covering sub-processors, data location, and breach notification.

Data residency (which region or country a tenant's data is stored in) is a configurable tenant setting, not a fixed platform default.

## 8. Business Continuity & Reliability

Enterprise tenants plan their own operations around the platform's availability guarantees. Those guarantees are explicit, measured, and published — not implied.

- **Recovery Point Objective (RPO)** and **Recovery Time Objective (RTO)** targets defined per subscription tier and published to tenants as part of the service agreement.
- Automated, encrypted backups on a defined schedule, with periodic restore testing — a backup is not considered valid until a restore has been verified.
- Multi-region or multi-zone failover for core platform services, consistent with the tenant's configured data residency.
- A public status page communicating real-time platform availability and historical incident/uptime transparency.
- Documented disaster recovery runbooks, reviewed and tested on a recurring schedule.

## 9. Governance Model

Control over the platform splits cleanly between two roles: the Super Admin, who governs the platform as a whole, and the Tenant, who governs its own configured instance within those boundaries.

### 9.1 Super Admin Philosophy

The Super Admin governs the platform end-to-end:

| Domain | Scope |
|---|---|
| Platform | Entire Platform · Entire Marketplace · Entire Module Ecosystem · Entire AI Ecosystem · Entire API Ecosystem · Entire Deployment Policies |
| Commercial | Entire Subscription · Affiliate Program Management · Commission Rules · Referral Policies · Payout Management |
| Brand & Tenancy | Entire Branding Standards · Entire Tenant Lifecycle |
| Security & Identity | Entire Security Policies · Entire Identity Management · Entire Authentication Policies · Entire Authorization Policies · Entire API Security · Entire Session Management · Entire License Management · Entire Device Management |

Authentication policy configurability and risk-based adaptive authentication (both Section 6.3) are administered exclusively by the Super Admin role.

### 9.2 Tenant Philosophy

Within the boundaries the Super Admin sets, each tenant independently configures its own instance according to its subscription plan — without modifying source code:

| Domain | What Tenants Configure |
|---|---|
| Brand & Presentation | Branding · Domains · Website · CMS · Dashboard · Themes |
| Applications | Mobile Application · Desktop Application · Desktop Application Settings |
| Business Logic | Business Modules · Workflows · Automation · Reports · Notifications |
| Integrations | API Key Integrations · AI Provider Keys · Third-Party Service Keys · Database Connections (where architecture permits) · API Endpoint Configuration |
| Synchronization | Desktop Synchronization · Mobile Synchronization · Automatic Background Synchronization · Offline Mode · Offline Sync Policies · Online Sync Policies · Background Synchronization Rules · Local Storage Policies |
| Access & Devices | Device Registration · Device Management · Authorization Policies · Authentication Settings · License Management |
| Deployment | Deployment Policies · Desktop Auto Updates |
| Growth Programs | Affiliate Program Settings · Commission Configuration · Referral Rules & Reward Policies · Payout Methods |

Tenant-configurable Authentication Settings draw from the full authentication method catalog (Section 6.1) and the digital identity/signature provider catalog (Section 6.2), scoped by whatever the tenant's subscription plan and Super Admin policy allow.

## 10. Configuration & Extensibility Philosophy

Business logic avoids source code changes wherever possible. The platform's evolution path is layered, in order of preference:

**Configuration → Metadata → Templates → Rules → Policies → Plugins → Automation → AI Assistance → Server Validation → API Authorization → Client Access**

— instead of hardcoding. Each layer is exhausted before the next is introduced; source code changes are the last resort, not the first response to a new business need.
